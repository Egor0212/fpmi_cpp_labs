# Расчетно-графическая работа №2. STL. Последовательные контейнеры

Представьте, что вы разрабатываете основу (ядро) для музыкального стримингового сервиса, позволяющего работать с треками. Трек (`Track`) в свою очередь должен содержать информацию о своём `id` (**уникальный** идентификатор), названии (`title`), исполнителе (исполнителях) (`singers`) и длительности (`duration`).

За основу возьмём класс `MusicManager`, содержащий в себе три различных контейнера для хранения треков: **основной плейлист**, **очередь "Играть далее"** и **история прослушиваний**.

### Основной плейлист
Треки, проигрывающиеся последовательно. Основные запросы, поступающие от пользователя:
- включить трек с номером $N$;
- перемотать на $N$ треков вперёд / назад;
- поменять треки местами.

### Очередь "Играть далее"
Временная очередь. Основные запросы, поступающие от пользователя:
- добавить трек в начало очереди (т.е. сыграть следующим);
- добавить трек в конец очереди;
- система сама удаляет трек из начала очереди, когда он проигран.

### История прослушиваний
Лог последних прослушанных треков. Новые треки добавляются в начало. Размер истории ограничен (последние $M$ треков), при достижении лимита старые треки удаляются из конца. Каждые $K$ добавленных треков история сохраняется в файл `history.txt`. Пользователь может удалять конкретные треки из истории (текстовый файл также должен измениться).
